How Steer is designed

An agent that can change your code in a minute makes the person reviewing it the bottleneck. Steer is a working sketch of the other half of that job: the interface where a person sets an agent's course, watches it work, corrects it without starting over, and decides what ships. Each choice below rests on what people building and using these tools have found.

1The plan is a document you edit before anything is spent

Agents that plan first and then work out of sight leave the person to find out late that the approach was wrong. Devin added interactive planning so a person can change the approach before compute is spent. Steer opens on the agent's proposed plan, already editable: rename a step, move it, drop it, add your own. Nothing runs until you approve it.

Beside the plan, the agent shows what it read and what it is assuming, so a wrong assumption is caught before it becomes code. Correct one in a sentence and the assumption is struck through, the step it touches changes, and so does the code it writes. The plan also carries an estimate of time and cost, and the summary sets the actual beside it.

In Steer: the Plan column, with move, drop and add, and Approve plan and run; Before you approve, with It read and It assumes; the estimate above the plan.

Sources: Builder.io on Devin and Cursor, Latent Space on asynchronous agents.

2Never silent

People interrupt an agent when silence looks like a hang. So the current action is always on screen in plain words, under the step it belongs to, with time, cost and context running in the header. Each action lands in the feed with its time, so the record reads like a colleague's notes rather than a log.

In Steer: the line under the step that's running, the Activity feed, the meters.

Source: Tian Pan, designing the human-agent interaction layer.

3Steer is not stop

A new prompt throws away the plan and the work so far. A steer keeps both: it's queued, the agent reads it at the next step boundary, and only the steps after that change. Pause and Stop are separate controls with separate promises: pause holds everything, stop keeps every finished step. Each says what it keeps before you press it.

In Steer: send "Follow the system setting by default" while it's on step 2, and step 4 changes, marked "Changed by your steer". Nothing already done moves.

Sources: CopilotKit on agent steering, interruption, steering and handoff.

4Ask only where a person can decide

A confirmation on every action feels like oversight and catches little. Steer asks once, for the only action in the run that leaves the machine. The card names the commands, what they touch, whether they can be undone, and the evidence so far. It also offers the two other answers people want: review first, or do it myself.

In Steer: the push and pull request card, with Push and open PR, Review changes first, I'll do it myself.

Sources: building a good human-in-the-loop, Atlassian on approval and review, Smashing on consent patterns.

5Evidence before the verdict

Agents tend to report "All tasks completed". Steer's summary makes each claim with its proof beside it: which checks pass, that one failed first and how it was fixed, what was pushed and what wasn't, how many changes you've accepted.

In Steer: the summary when the run ends, and the Checks tab, where the failing run is kept, not overwritten.

Sources: show the agent's evidence first, Humans are missing from AI coding agent research.

6Checks hold the agent

A turn that changed files isn't done until the project's checks pass. When the contrast check fails, the failure is shown in full, the agent goes back and fixes it, and the passing run sits under the failing one. The same idea runs Leaftext's agent harness, where a failed check sends the agent back to work.

In Steer: step 5, and the two contrast runs in Checks.

7Review by intent, not by file

Review is now the ceiling on how fast work ships. A diff sorted by file makes the reviewer rebuild the agent's reasoning. Steer groups each change under the plan step that made it, puts the agent's reason above the diff, and lets you accept it or send it back with a note, which becomes a new step the agent runs.

In Steer: the Changes tab, with Accept and Send back on each change, a count of what is left to review, and only the changed part of a replaced line marked. J and K move between changes, A accepts, S sends back.

Sources: Latent Space with Cognition, coding agent fundamentals, UT Austin.

8Show the change, not only the code

A diff of color values doesn't tell you whether the page looks right. The Preview tab renders the settings page before and after, and the Appearance switch in it works, so the result is something you use, not something you imagine.

In Steer: the Preview tab, with Light and Dark.

9Every step is a checkpoint, and what can't be undone says so

Checkpoints cover file edits, not side effects. Steer lets you return to after any finished step and run the rest again, and the dialog says plainly when something already left the machine and won't come back.

In Steer: Return here on each finished step.

Source: building a good human-in-the-loop.

Steer is one hand-written HTML file with no framework and no build step: the whole interface, the scripted agent and the app it works on. No model runs and nothing leaves your browser. Light and dark, phone and desktop, keyboard and screen reader.
